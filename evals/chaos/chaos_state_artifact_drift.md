# Chaos scenario: the state file says `done`, the evidence is not on disk

## What this scenario exercises

`workflow_state.json` is the orchestrator's memory. Every resumed session, every
handoff, and every gate decision reads it. But it is a *description* of the
workspace, not the workspace itself, and the two drift apart constantly for
mundane reasons:

- the run moved machines and `02_data/clean.parquet` was too large to bring;
- a user tidied `03_analysis/` between sessions;
- a subagent wrote to a path that differs from the one the state file records
  by one directory (`04_results/` vs `03_analysis/results/`);
- a git operation — a branch switch, a stash, a partial checkout — left the
  state file from one commit beside the artifacts of another;
- Stage 6 was re-run and overwrote `main.tex`, but `04_results/` still holds the
  exhibits generated from the *previous* estimation.

The orchestrator's default posture is what makes this dangerous: it trusts its
own state file. A resumed session reads `stages.3_identification_estimation:
"done"`, `method_gate.status: "pass"`, and proceeds straight to writing — about
results it has never seen and which may no longer exist.

## The trigger

A session resumes and reads:

```json
{"stages": {"3_identification_estimation": "done", "4_tables_figures": "done"},
 "method_gate": {"status": "pass",
                 "method_gate_report": "03_analysis/method_gate.md"},
 "replication_pack": {"status": "ready", "master_script": "run_all.sh"}}
```

while the workspace contains no `03_analysis/method_gate.md` and no
`run_all.sh`. Nothing in the JSON is self-contradictory. It is simply false.

## Expected recovery path

Per SKILL.md (Phase 0 §7, 断点交接必须可恢复) and
`references/orchestration-and-handoff.md` §Fresh Evidence:

1. **Treat the handoff as a pointer, never as evidence.** The contract is
   explicit: `fresh_evidence_required` means a resumed session re-establishes
   the facts before acting on them. A stage passport saying "done" is a claim to
   be checked, not a result to be used.
2. **Run the mechanical check first, before any stage work.**

   ```bash
   python3 scripts/pw.py check <workspace>
   ```

   `check_workspace_gates.py` exists for exactly this: a gate marked `pass` or
   `ready` whose artifact is not on disk is a hard failure, not a warning.
3. **Demote, do not delete.** Every gate whose evidence is missing goes back to
   `pending` (not `not_pass` — the work may have been done correctly and then
   lost, which is a different fact from having failed). The owning stage returns
   to `in_progress`. Record the demotion in `decisions` with the reason, so the
   audit trail distinguishes "lost" from "never done".
4. **Re-derive rather than re-assert.** The missing artifacts are regenerated by
   re-running the stage — from `run_all.sh` where one exists, which is the
   entire reason the replication scaffold is frozen at Stage 3 rather than built
   at the end. Never restore a gate to `pass` by writing a placeholder file at
   the path the state file names.
5. **Check the inverse drift too.** Artifacts newer than the state file are the
   other half of this failure: exhibits in `04_results/` whose numbers no longer
   match `03_analysis/results/` mean Stage 4 must re-run before Stage 5 quotes
   them. `check_workspace_gates.py --reconcile` and
   `check_manuscript_numbers.py` are the mechanical form of that check.
6. **Snapshot before repairing.** `backups/after_stage<N>/` is the rollback
   path; a repair that destroys the evidence of what drifted makes the next
   occurrence undiagnosable.

The recovery is considered failed if any of the following hold:

- the session proceeds to Stage 5 on the strength of the state file alone;
- a placeholder or reconstructed-from-memory file is written to satisfy a gate;
- gates are demoted silently, with no `decisions` entry;
- the manuscript quotes numbers from exhibits that no longer trace to a results
  file (`check_manuscript_numbers.py` will catch this, but only if it is run);
- the state file is edited to remove the gate rather than to demote it.

## How a maintainer verifies this scenario

Delete a load-bearing artifact from a green workspace and confirm the gate
runner refuses it:

```bash
rm <workspace>/03_analysis/method_gate.md
python3 scripts/pw.py check <workspace>     # must exit non-zero
```

The failure row must name the gate and the missing path:

```
[FAIL] method_gate  status=pass but missing 03_analysis/method_gate.md
```

Then confirm the recovery is recorded rather than papered over — `decisions`
should carry a line of the form:

```
2026-08-27 resumed session: method_gate.status pass -> pending; evidence
  03_analysis/method_gate.md absent on disk (workspace moved from host A);
  re-running Stage 3 from run_all.sh rather than reconstructing the report.
```

## Status

**Based on inference, refine on first real failure.** The mechanical half is
implemented and enforced — `check_workspace_gates.py` has caught
evidence-free gate claims since the gate battery existed. What is inferred is
the *demote-don't-delete* convention in step 3 and the `pending` vs `not_pass`
distinction; a real drift incident should confirm or correct it.
